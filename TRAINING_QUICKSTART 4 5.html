🤖 How to build this with AI
Each step gives you an AI Coding Prompt — a contract describing what a file must do. You paste it into your assistant; it writes the code. You review, run, and iterate.
★
The build loop — paste, review, run, iterate
Prompt engineering + a human-in-the-loop review at every file
Read once ▼

The prompts are deliberately provider-agnostic contracts: they describe what each file must do, and your AI assistant writes how. This is the same discipline the pipeline itself uses — the LLM writes the rules, deterministic Python does the work.

Recommended workflow with Claude Code

  1. Open your project folder in Claude Code — run claude in a terminal at the project root, or use the VS Code / JetBrains extension.
  2. Paste the step's AI Coding Prompt as your message.
  3. Review the plan. In Plan Mode, Claude Code proposes which files it will create or change — read it before approving.
  4. Approve the edits. It shows each change and asks permission — nothing is written or run without your OK.
  5. Run the step's Quick test / Checkpoint to confirm the file actually works.
  6. Iterate on errors — paste any error message back and ask it to fix; repeat until the checkpoint is green.
  7. Only then move to the next step. Build in order — every agent imports from core/.
Tips that make this go smoothly
  • Keep .env out of version control (add it to .gitignore) — never share your token.
  • Ask the assistant to explain any code you don't understand — you are learning, not just generating.
  • If it over-engineers, say "keep it minimal and match the prompt exactly."
  • Commit (or copy) after each step that passes its checkpoint, so you can always roll back.
Concepts you are practising

Prompt engineering (the contracts below), context engineering (feeding the model schemas & profiles, not raw rows), loop engineering (the HITL approve/iterate cycle), and harness engineering (the tools, state, and audit trail around the model).

3
Profiler Agent — Understand the Raw Data
Scan every CSV and compute quality stats — pure Python, no LLM
🔶 Phase 1a · ~20 min ▼

What the profiler does (no writes to the data layers yet)

The profiler reads every input CSV and, for each column, computes: dtype, null percentage, unique count, sample values, and numeric min/max/mean. It also flags quality issues like mixed date formats and finds candidate join keys. This is deterministic Python — it does not call the LLM. Output is a single JSON file that the STTM generator will read.

Key output structure

{
  "run_id": "20260718_191117",
  "tables": {
    "sales_data": {
      "row_count": 186,
      "columns": {
        "transaction_date": {
          "dtype": "object", "null_pct": 0.0, "unique_count": 186,
          "sample_values": ["01/15/2024", "2024-01-17", "..."],
          "quality_flags": ["mixed_date_formats"]
        }
      }
    }
  },
  "candidate_join_keys": { "product_id": ["sales_data", "products"] }
}
AI Coding Prompt
"""
Create agents/profiler.py. Main function:
  def profile(file_paths: list[str], run_id: str) -> str

NO LLM in this agent - it is pure pandas.

Requirements:
1. Load each CSV with pd.read_csv(fp, low_memory=False)
2. For every column compute: dtype (as str), null_count, null_pct,
   unique_count, sample_values (up to 5 distinct non-null values),
   and min/max/mean for numeric columns.
3. Detect quality flags per column:
   - "mixed_date_formats": object column where >10% of values match
     MM/DD/YYYY AND >10% match YYYY-MM-DD
   - "possible_abbreviations": object column with avg string length < 6
4. Find candidate join keys: column names ending in "_id" that appear
   in 2 or more tables.
5. Write the full profile dict to:
   PROFILES_DIR / f"profile_combined_{run_id}.json"
6. Log with AuditLogger (agent="profiler", action="completed").
7. Return the output file path.

Import path constants from core.config, AuditLogger from core.audit.
"""
Key Insight — context engineering

The profiler turns dirty raw data into a compact, structured summary. That summary — not the raw rows — is what the STTM generator feeds to the LLM in Step 4. Small, factual context = cheaper, more reliable LLM calls.

Quick test

print('Profile written to:', path)
"

Checkpoint

  • ✓ Profile JSON written under data/profiles/ with the timestamp run id
  • ✓ mixed_date_formats flag appears on transaction_date
  • ✓ candidate_join_keys lists product_id and store_id
4
STTM Generator — The Transformation Contract
The LLM converts the profile into Bronze, Silver & Gold rule CSVs (LLM calls 1–3)
🔶 Phase 1b–3b · ~30 min ▼

What is an STTM?

Source-to-Target Mapping — a CSV where each row is one transformation rule. Agents read their STTM and execute it in Python. This separates what to do (STTM, LLM-generated) from how to do it (agent code, deterministic Python). These are 3 of the 4 LLM calls in the whole pipeline.

ColumnExampleMeaning
source_schemalandingOrigin schema/layer
source_tablesales_dataOrigin table name
source_columntransaction_dateColumn to transform (* = table-level)
target_schemabronzeDestination schema/layer
target_tablesales_data_bronzeDestination table name
target_columntransaction_dateOutput column name
transformation_typetype_castCategory of rule
transformation_logicdatetimeImplementation hint the agent reads

Supported transformation logic (what the agents in Steps 5–7 understand)

Bronze — fidelity only:

  • type_cast — datetime / float / int / str
  • metadata_inject — _load_timestamp, _source_file
  • passthrough — copy as-is

Silver — cleanse:

  • drop null / fill null (mean/median/mode/0)
  • date — normalise to YYYY-MM-DD
  • lowercase / uppercase / title case
  • strip · deduplicate · surrogate_key

Gold — analytics (intent-driven): join (join_left:table_a:table_b:key) · group_by · aggregate (SUM, AVG, COUNT, MAX, MIN)

AI Coding Prompt
"""
Create agents/sttm_generator.py with three public functions and a
shared LLM helper (GitHub Models via LangChain - see the LLM pattern
in the Reference Card).

1. generate_bronze_sttm(profile_path, business_intent, run_id) -> str
   - Read the profile JSON
   - Build a prompt with: table schemas, sample values, quality flags
   - Ask the LLM for a CSV with the 8 required columns:
     source_schema, source_table, source_column, target_schema,
     target_table, target_column, transformation_type, transformation_logic
   - Rules to generate: type_cast for every column (infer type from
     dtype/flags), plus metadata_inject rows for _load_timestamp and _source_file
   - Parse the CSV from the response (look for a ```csv fence first, then raw CSV)
   - Validate the required columns exist, save to
     STTM_DIR / f"sttm_bronze_{run_id}.csv"; return the path.
     Bronze is intent-agnostic - map every column.

2. generate_silver_sttm(bronze_paths, bronze_sttm_path, business_intent, run_id) -> str
   - Read the bronze parquet files (pandas) for schemas + sample values
   - Include the prior Bronze STTM as context
   - Ask the LLM for Silver cleansing rules: drop/fill null, date standardise,
     text normalise (lower/upper/title/strip), deduplicate, surrogate_key
   - Save to STTM_DIR / f"sttm_silver_{run_id}.csv"; return the path.

3. generate_gold_sttm(silver_paths, silver_sttm_path, business_intent, run_id) -> str
   - Read the silver parquet schemas; include the prior Silver STTM as context
   - Ask the LLM for Gold rules that answer business_intent:
     join rules (format join_left:table_a:table_b:key), group_by columns,
     aggregate columns (SUM/AVG/COUNT). Gold IS shaped by the intent.
   - Save to STTM_DIR / f"sttm_gold_{run_id}.csv"; return the path.

Helpers: _extract_csv(text) (```csv fence first, then raw) and
_validate_and_save(csv_text, out_path) (check the 8 required columns).
Log each generation with AuditLogger. Use full run_id in filenames (no truncation).
"""
Tip — inspect STTM output manually

After building this, generate a Bronze STTM and open the CSV in a spreadsheet. You should see one row per column of each CSV plus two metadata_inject rows per table. This is the contract the Bronze Agent will execute — and the thing you approve at the first HITL gate.

Checkpoint

  • ✓ sttm_bronze_<run_id>.csv has the 8 required columns
  • ✓ The transaction_date row has type_cast / datetime
  • ✓ Two metadata_inject rows per source table

Bronze Agent — CSV to Parquet with Type Casting
Executes the approved Bronze STTM in pandas — deterministic, no LLM
🔶 Phase 2a · ~20 min ▼

Bronze layer contract

Bronze is the fidelity layer — no business logic, no joins. Only: type casting, column renaming, and two metadata columns. Row count in = row count out. No LLM: the agent just applies the STTM rules with pandas.

Input (per table):

  • Raw CSV file
  • The approved Bronze STTM slice for this table

Output (per table):

  • Parquet in data/bronze_layer/
  • All columns type-cast
  • _load_timestamp, _source_file added
AI Coding Prompt
"""
Create agents/bronze_agent.py. Main function:
  def run(input_files: list[str], sttm_path: str, run_id: str) -> list[str]

NO LLM - deterministic pandas execution of the approved STTM.

For each input CSV:
1. Extract the table name from the filename stem ("sales_data.csv" -> "sales_data")
2. Read the STTM CSV; filter rows whose source_table matches this table
3. Read the CSV with pd.read_csv(fp)
4. For each STTM rule:
   - type_cast: apply per transformation_logic
       datetime -> pd.to_datetime(col, errors="coerce")
       float    -> pd.to_numeric(col, errors="coerce")
       int      -> pd.to_numeric(col, errors="coerce").astype("Int64")
       str      -> col.astype(str)
     and rename source_column -> target_column
   - passthrough: copy the column unchanged
   (skip metadata_inject rows here - handled next)
5. Inject metadata columns in Python:
   df["_load_timestamp"] = datetime.now(timezone.utc).isoformat()
   df["_source_file"]    = str(fp)
6. Write BRONZE_DIR / f"{table}_bronze_{run_id}.parquet"
   with df.to_parquet(..., index=False)
7. Audit-log the input_shape and output_shape.
Return the list of written parquet paths.
"""
Why deterministic?

Keeping Bronze/Silver/Gold in pure Python is the core efficiency of this design: the LLM writes the rules once (the STTM), and cheap, reproducible Python does the heavy data work every time. That is why the whole pipeline needs only 4 LLM calls.

Checkpoint

  • ✓ 3 Parquet files written to data/bronze_layer/
  • ✓ pd.read_parquet(...).dtypes shows datetime64 for transaction_date
  • ✓ Row count equals the source CSV row count (~186 for sales_data)
  • ✓ _load_timestamp and _source_file columns present
6
Silver Agent — Cleanse, Standardize & Deduplicate
Applies the Silver STTM in pandas: nulls, dates, text, dedup, surrogate keys — no LLM
⬜ Phase 3a · ~25 min ▼

Silver layer contract

Silver is the quality layer. It reads Bronze Parquet and applies cleansing rules from the Silver STTM. Row count may decrease (dedup). A surrogate integer key is added as the first column. No LLM — the agent reads each rule's transformation_logic keyword and runs the matching pandas operation.

How the agent maps logic keywords to pandas

transformation_logic contains…pandas operation
drop null / remove nulldf.dropna(subset=[col])
fill null + mean/median/mode/0df[col].fillna(df[col].mean()/median()/mode()/0)
date / datetimepd.to_datetime(col, errors="coerce").dt.strftime('%Y-%m-%d')
integer / float / numericpd.to_numeric(col, errors="coerce")
lowercase / uppercase / title casecol.str.lower() / .upper() / .title()
strip / trimcol.str.strip()
deduplicdf.drop_duplicates()
AI Coding Prompt
"""
Create agents/silver_agent.py. Main function:
  def run(bronze_paths: list[str], sttm_path: str, run_id: str) -> list[str]

NO LLM - deterministic pandas.

For each bronze parquet file:
1. Read it with pd.read_parquet(fp)
2. Match STTM rows to this table using flexible matching:
   compare on the file stem AND the stem with "_bronze_<run_id>" stripped.
3. For each rule, inspect transformation_logic (lowercased) and apply the
   matching pandas op (see the keyword -> pandas table above):
   drop/fill null, date standardise to YYYY-MM-DD, numeric casts,
   lower/upper/title case, strip, deduplicate. Rename source_column ->
   target_column when they differ.
4. Insert a surrogate key as the FIRST column:
   df.insert(0, f"pk_{base_name}_silver_id", range(1, len(df)+1))
5. Keep only the STTM-approved target columns (plus the surrogate key).
6. Write SILVER_DIR / f"{base_name}_silver_{run_id}.parquet"
7. Audit-log input_shape and output_shape.
Return the list of written paths.
"""
Design Note

Silver only unifies categories if the STTM contains a normalise rule for that column. If the LLM did not generate one, abbreviations like Elec. vs ELECTRONICS persist to Gold — visible in the report as separate rows. That is expected, and it is exactly what the HITL gate lets you catch and fix by editing the STTM.

Checkpoint

  • ✓ 3 Silver Parquet files in data/silver_layer/
  • ✓ transaction_date values all match the YYYY-MM-DD pattern
  • ✓ pk_sales_data_silver_id is the first column and starts at 1
  • ⚠ Row count ≤ Bronze (dedup may reduce it slightly)
7
Gold Agent — Join, Group & Aggregate for Analytics
Merges Silver tables and aggregates per the Gold STTM — deterministic, no LLM
🥇 Phase 4a · ~20 min ▼

Gold layer contract

Gold is the analytics layer — table(s) purpose-built for the business question. It joins Silver tables on common ID columns and applies GROUP BY + aggregations. Result sets are typically <50 rows. No LLM — the agent executes the Gold STTM's join / group_by / aggregate rules with pandas.

STTM Gold rule format the agent reads

# join rule
transformation_type  = join
transformation_logic = join_left:sales_data_silver:products_silver:product_id
# -> df = sales_data_silver.merge(products_silver, on="product_id", how="left")

# aggregate rule
transformation_type  = aggregate
transformation_logic = SUM(total_amount) AS total_revenue

# group_by rule
transformation_type  = group_by
target_column        = category
AI Coding Prompt
"""
Create agents/gold_agent.py. Main function:
  def run(silver_paths: list[str], sttm_path: str,
          business_intent: str, run_id: str) -> list[str]

NO LLM - deterministic pandas.

1. Load every silver parquet into a dict keyed by clean table name
   (register a few name variants so matching is forgiving).
2. Group STTM rows by target_table to know which Gold table(s) to build.
3. For each target Gold table:
   - Parse join rules "join_left:A:B:key" and merge with pandas:
       df = tables[A].merge(tables[B], on=key, how="left")
   - Apply column renames (source_column -> target_column).
   - Apply group_by + aggregate rules:
       df.groupby(group_cols).agg({col: "sum"/"mean"/"count"/...}).reset_index()
   - Keep only the STTM-approved target columns.
   - Insert a surrogate key: df.insert(0, "pk_gold_id", range(1, len(df)+1))
4. Write GOLD_DIR / f"{target_table}_{run_id}.parquet"
5. Audit-log. Return the list of written paths.
"""

Checkpoint

  • ✓ 1 Gold Parquet file in data/gold_layer/
  • ✓ Row count much smaller than Silver (aggregated — typically 8–30 rows)
  • ✓ Columns include an aggregate like total_revenue
  • ✓ pk_gold_id starts at 1

Reporter — Generate the HTML Analytics Report
The LLM writes the analysis SQL + narrative (LLM call 4); DuckDB executes it; Plotly renders the charts
📊 Phase 4b · ~25 min ▼

What the reporter produces

A self-contained HTML file with: an executive answer, interactive Plotly charts, a data table, and the SQL that produced the results. Opens in any browser, no server needed. This is the 4th and final LLM call.

LLM output format (the 4th LLM call)

SQL:
```sql
SELECT category, SUM(total_revenue) AS revenue
FROM gold_table GROUP BY category ORDER BY revenue DESC
```

NARRATIVE:
Electronics led Q1 2024 with $142,500 in revenue (38% of total),
followed by Home & Kitchen at $95,000 (25%)...

CHARTS:
```json
[
  {"type": "bar", "x": "category", "y": "revenue", "title": "Revenue by Category"},
  {"type": "pie", "x": "category", "y": "revenue", "title": "Revenue Share"}
]
```
AI Coding Prompt
"""
Create agents/reporter.py. Main function:
  def generate_report(gold_paths: list[str],
                      business_intent: str, run_id: str) -> str

This agent DOES use the LLM (call 4 of 4) - via the same GitHub Models
helper as the STTM generator.

1. Load the gold parquet files into an in-memory DuckDB connection
   (conn.register / read_parquet). DuckDB executes the SQL deterministically.
2. Build a schema context string: table names, columns, types, a few sample rows.
3. ONE LLM call: send schema + business_intent, ask for three labelled sections:
     SQL:       a DuckDB SELECT that answers the question
     NARRATIVE: a 2-3 paragraph executive summary
     CHARTS:    a JSON array of chart specs {type, x, y, title}
4. Parse the response: _extract_sql (```sql fence, then bare SELECT),
   _extract_narrative (text after "NARRATIVE:"),
   _extract_json_block (```json after "CHARTS:").
5. Execute the SQL via DuckDB (retry once if it errors; fall back to
   SELECT * FROM first_gold_table LIMIT 20).
6. Render charts with plotly.express (bar/pie/line) -> fig.to_html(full_html=False).
7. Build the data table with df.to_html(index=False).
8. Assemble a self-contained HTML page: header with the business_intent,
   an Executive Answer card (narrative), a Charts grid, a Data Table card,
   and the SQL in a <pre> block. Footer: run_id + timestamp.
9. Write REPORTS_DIR / f"report_{run_id}.html"
   and REPORTS_DIR / f"report_{run_id}.json" (a machine summary).
10. Audit-log. Return the HTML path.
"""
Tip — build the template with test data first

Only the Gold STTM changes — different GROUP BY columns and aggregations. Bronze and Silver STTMs stay the same (they are intent-agnostic quality rules). That is the power of the medallion architecture: re-use clean Bronze/Silver data to answer many different questions.

LLM client pattern — GitHub Models via LangChain (paste into any agent that needs the LLM)

from core.config import GITHUB_TOKEN, GITHUB_BASE_URL, GITHUB_MODEL

_llm = None

def _make_llm():
    """GitHub Models is an OpenAI-compatible endpoint, so we use LangChain's
    ChatOpenAI with a custom base_url."""
    global _llm
    if _llm is None:
        from langchain_openai import ChatOpenAI
        _llm = ChatOpenAI(
            api_key=GITHUB_TOKEN,
            base_url=GITHUB_BASE_URL,      # https://models.github.ai/inference
            model=GITHUB_MODEL,            # openai/gpt-4.1-mini
            temperature=0,
        )
    return _llm

def _call_llm(prompt: str) -> str | None:
    try:
        return _make_llm().invoke(prompt).content
    except Exception as e:
        print(f"[LLM] call failed: {e}")
        return None
Swapping providers later

Because everything goes through _make_llm(), you can support Groq / Anthropic / Gemini by branching on LLM_PROVIDER and returning the matching LangChain chat model — the rest of the pipeline never changes.
